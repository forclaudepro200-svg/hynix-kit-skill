# hynix-followup

후속 서술형(6문항, 문항당 5분, AI 금지, 붙여넣기 불가)은 제출물과 작업 기록으로 출제된다. 제출 전에 **내가 내 말로 답할 수 있도록** 내 작업을 설명해 준다. 답안 문장을 대신 써 주는 것이 아니라, 내가 기억하고 설명할 재료를 정리한다.

## 읽을 것 (토큰 절약: 필요한 부분만)
- README.md 요구사항, PLAN.md 0절(제출물)·3절(성공 기준)·4절(데이터 규칙)
- DECISIONS.md 결정 표, **AI 제안 검토 기록**, 핵심 코드 이해 메모
- HANDOFF.md 실행 방법·충족표·미검증·남은 한계
- `git log --oneline`, 테스트 실행 결과(직접 한 번 실행)
- 핵심 판정·계산 함수 2~3개 (파일 전체가 아니라 함수만)

## FOLLOWUP_PREP.md 구성

### 1. 내 서비스 한 문단 설명
누가 어떤 문제로 쓰는지, 입력 → 처리 → 출력 흐름을 중학생도 이해할 말로 5문장 이내로 쓴다.

### 2. 핵심 동작과 확인 방법
핵심 동작 3~5개를 표로 정리한다. **실제로 실행한 확인만** 적고, 하지 않은 것은 "미검증"으로 쓴다.
| 동작 | 코드 위치 | 어떻게 확인했나 (명령·테스트 이름) | 실제 결과 (숫자) |

### 3. AI 제안을 확인·수정한 부분
DECISIONS.md `AI 제안 검토 기록`과 커밋 메시지(정정·수정·변경)에서 2~3건을 고른다. 건마다:
- AI가 처음 제안한 것
- 내가 무엇을 보고 이상하다고 판단했나(테스트 실패, 담당자 발언, 데이터 확인)
- 어떻게 바꿨고, 바뀐 것을 어떻게 확인했나
기록이 없으면 지어내지 말고 "기록 없음 — 사용자가 기억하는 사례를 직접 적을 것"이라고 쓴다.

### 4. 예상 질문 6개와 답변 뼈대
유형을 섞는다: 핵심 동작·확인 방법 1, AI 제안 확인·수정 1, 왜 이렇게 구현했나 1, 실패하면 어떻게 되나 1, 데이터 규칙·경계값 1, 더 시간이 있으면 무엇을 검증·개선하나 1. 각 질문은 실제 파일·함수·결정 번호를 짚는다.
답변 뼈대는 **키워드로만** 쓴다(문장 금지).
```
Q1. <질문>
- 위치: <파일:함수 / D번호 / A번호>
- 한 일 → 이유 → 확인 방법 → 약점 → 파급 → 다음
```

### 5. 외울 숫자
입력·제외·처리 행 수, 테스트 수와 통과 수, 임계값, 성공 기준 충족 개수 등 답변에 쓸 실제 수치.

### 6. 답변 요령 (그대로 둔다)
- 첫 문장에 결론, 둘째 문장에 근거(파일·테스트·숫자).
- 질문의 전제가 실제 구현과 다르면 **차이부터 밝히고** 내 작업을 설명한다.
- 모르는 것·안 한 것은 "검증하지 못했다"고 쓰고 다음에 할 확인을 적는다.

## 절차
1. 위 파일을 읽고 테스트를 한 번 실행한다.
2. 문서와 코드가 다르면 **코드 기준**으로 쓰고, 불일치를 맨 위에 `주의` 목록으로 적는다.
3. FOLLOWUP_PREP.md에 저장하고 커밋한다(`docs: 서술형 대비 정리`). 실패하면 직접 실행할 명령을 보고한다.
4. 화면에는 1절 한 문단과 예상 질문 6개만 보여 주고 멈춘다.

## 하지 말 것
- 하지 않은 검증이나 없었던 AI 수정 사례를 지어내지 않는다.
- 제출해야 하는 코드·결과물을 이 단계에서 고치지 않는다(문제를 발견하면 보고만 한다).
