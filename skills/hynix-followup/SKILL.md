# hynix-followup

후속 서술형(6문항, 문항당 5분, AI 금지, 붙여넣기 불가)은 제출물과 작업 기록으로 출제되고, 어떤 질문이 나올지 모른다. 그래서 **내가 한 작업 전체를 내가 설명할 수 있게** 자세히 풀어 준다. 답안 문장을 대신 쓰는 게 아니라, 어떤 질문에도 꺼내 쓸 수 있는 재료를 정리한다.

## 읽을 것
- README.md 전체, PLAN.md 전체, INTERVIEW.md 전체
- DECISIONS.md 전체(결정 표, AI 제안 검토 기록, 핵심 코드 이해 메모), HANDOFF.md 전체, VERIFY.md(있으면)
- `git log --stat` (커밋 순서가 곧 작업 순서다)
- 소스 코드의 모든 주요 함수, 테스트 파일의 테스트 이름과 단언
- 테스트를 한 번 실행하고, 실행 명령(HANDOFF)이 있으면 한 번 실행해 실제 출력을 얻는다

## FOLLOWUP_PREP.md 구성
모든 절에서 **근거(파일:함수, 테스트 이름, 커밋 해시, D·A 번호, 담당자 발언, 실제 숫자)**를 붙인다. 근거가 없는 내용은 쓰지 않는다. 쉬운 말로 쓰되 빠짐없이 쓴다.

### 0. 30초 요약 (제출 직전 마지막으로 읽을 것)
- 한 문장 정의, 핵심 숫자 5개, 내가 가장 잘한 판단 1개, 가장 큰 한계 1개

### 1. 문제 이해
- 누가, 어떤 업무에서, 무엇 때문에 곤란했나. 처음 README만 보고 이해한 것과 인터뷰 후 달라진 것.

### 2. 인터뷰와 요구사항 발견
- 담당자에게 물은 질문과 받은 답(중요한 것부터), README에 없던 숨은 요구사항, 그것이 PLAN의 어느 기준·규칙이 되었는지.
- 아직 확인하지 못한 것.

### 3. 성공 기준과 범위
- 기준(C0, C1…)마다: 무엇을, 왜 이 수치로, 어떻게 측정하는지, 충족 여부와 근거 테스트.
- 범위에서 뺀 것과 뺀 이유.

### 4. 작업 과정 (시간순)
- 커밋 순서대로 단계별로: 무엇을 했나 → 왜 그 순서였나 → 결과. 작업을 어떻게 나눴는지(작업 분해)가 보이게 쓴다.

### 5. 코드가 실제로 동작하는 방식
- 입력 → 처리 → 출력 흐름을 단계별로.
- 주요 함수마다: 파일:함수, 하는 일 한 줄, 입력·출력, 핵심 분기(경계값·예외 처리), 깨질 수 있는 입력.
- 데이터 규칙(시간대, 중복, 결측, 제외 대상, 경계값)을 코드 어디에서 어떻게 처리하는지.

### 6. 결정과 근거
- DECISIONS의 결정마다: 선택, 버린 대안, 근거, 검증. 요구사항이 바뀐 경우 이전 → 이후와 이유.

### 7. 검증
- 테스트 목록: 이름, 무엇을 검사하나, 결과. 경계값·빈 입력·중복·잘못된 형식 중 무엇을 검사했고 무엇을 못 했나.
- 실제 실행 결과(명령과 출력 숫자). 거짓 성공(0건 PASS 등)을 어떻게 막았나.
- **미검증 목록**과 각각 어떻게 확인할지.

### 8. AI 활용과 검토
- AI에게 무엇을 맡기고 무엇을 내가 판단했나(역할 분담), AGENTS.md에 둔 규칙과 이유.
- AI 제안을 확인·수정·거절한 사례(A 번호, 테스트 실패로 고친 커밋, 정정 커밋): 처음 제안 → 이상하다고 본 근거 → 수정 → 확인.
- 기록이 없으면 지어내지 말고 "기록 없음 — 사용자가 기억하는 사례를 직접 적을 것"이라고 쓴다.

### 9. 한계, 리스크, 실패 대응
- 남은 한계마다: 어떤 상황에서 문제가 되나 → 누가 무엇을 잘못 판단하게 되나(파급) → 감지 방법 → 대응·개선.
- "만약 ~라면?" 시나리오 5개 이상: 데이터가 10배, 새 형식·결측 증가, 담당자 규칙 변경, 서버·실행 실패, 경계값 오판 등. 각 시나리오에 현재 코드의 동작과 대응.

### 10. 질문 유형별 답변 재료
아래 유형마다 위 절의 어디를 쓰면 되는지 2~4개 키워드와 근거 번호로 연결한다.
핵심 동작·확인 방법 / 왜 이렇게 구현했나 / 대안을 왜 버렸나 / AI 제안 확인·수정 / 요구사항을 어떻게 파악했나 / 데이터 규칙·경계값 / 실패하면 어떻게 되나 / 테스트로 무엇을 보장하나 / 한계와 다음 단계 / 다시 한다면 무엇을 바꾸나 / 작업을 어떻게 나눴나 / 시간 배분

### 11. 외울 숫자
입력·제외·처리 행 수, 테스트 수와 통과 수, 임계값, 기준 충족 개수, 커밋 수 등.

### 12. 답변 요령 (그대로 둔다)
- 첫 문장에 결론, 둘째 문장에 근거(파일·테스트·숫자), 셋째 문장에 한계나 다음 단계.
- 질문의 전제가 실제 구현과 다르면 **차이부터 밝히고** 내 작업을 설명한다.
- 모르는 것·안 한 것은 "검증하지 못했다"고 쓰고 다음에 할 확인을 적는다.

## 절차
1. 위 파일을 읽고 테스트와 실행 명령을 한 번씩 실행한다.
2. 문서와 코드가 다르면 **코드 기준**으로 쓰고, 불일치를 맨 위 `주의` 목록에 적는다.
3. FOLLOWUP_PREP.md에 저장하고 커밋한다(`docs: 서술형 대비 정리`). 실패하면 직접 실행할 명령을 보고한다.
4. 화면에는 0절(30초 요약)과 `주의` 목록만 보여 주고 멈춘다.

## 하지 말 것
- 하지 않은 검증, 없었던 인터뷰 답변, 없었던 AI 수정 사례를 지어내지 않는다.
- 제출해야 하는 코드·결과물을 이 단계에서 고치지 않는다(문제를 발견하면 `주의`에 적는다).
