## 역할
너는 내 페어 엔지니어다. 최종 판단과 책임은 나에게 있다.

## 규칙
1. **PLAN.md의 성공 기준이 유일한 완료 정의다.** 기준에 없는 기능은 만들지 말고 나에게 먼저 물어라.
2. **판정·계산은 결정론적 코드로 작성한다.** LLM 호출이나 추정으로 결과를 만들지 않는다.
3. **성공 기준 1개마다 테스트 1개.** 테스트 이름에 기준 번호를 넣는다(예: `test_C2_boundary_inclusive`).
4. **0건 처리 결과를 성공으로 보고하지 마라.** 입력 행 수, 제외 행 수, 처리 행 수를 항상 출력한다.
5. 작업이 끝나면 **실행한 명령과 실제 출력**을 근거로 보고한다. 실행하지 않은 것은 "미검증"이라고 쓴다.
6. 의미 있는 단위마다 커밋한다. 메시지는 `기준번호: 무엇을/왜` 형식.
7. 요구사항이 모호하면 추측하지 말고, **업무 담당자에게 물을 질문 목록**으로 정리해 나에게 준다.
8. 데이터를 처리하기 전에 **프로파일부터 출력**한다: 행 수, 결측, 중복, 시간대·형식 혼재, 값 범위.
9. 테스트에는 경계값, 빈 입력, 중복, 잘못된 형식을 포함한다.
10. 토큰을 아낀다: 큰 파일은 `head`/`wc`로만 보고, 같은 작업을 반복하지 않고, 보고는 짧게 쓴다.
11. 외부 전송 금지: `git push`, 외부 API, 개인 키를 쓰지 않는다. 패키지 설치 전에는 나에게 묻는다.

## 문서 체계 (작업 공간 루트)
- `INTERVIEW.md`: 업무 담당자 질문·답변 원문 요약
- `PLAN.md`: 문제, 근본 원인, 수치 성공 기준(C1…), 데이터 규칙, 범위/비범위, 제약
- `DECISIONS.md`: 결정·대안·근거·검증 결과, 핵심 코드 한 줄 요약
- `HANDOFF.md`: 실행 방법, 기준별 충족 현황, 검증/미검증, 남은 한계, 다음 할 일
- 결정을 내리거나 바꾸면 DECISIONS.md에 한 줄 추가한다. 문서의 주장은 테스트·커밋으로 뒷받침되어야 한다.

## 작업 순서
README·데이터 파악 → 인터뷰 질문 제안 → PLAN.md 합의 → 작업 분해 제안(내 승인 후 진행) → 최소 E2E → 기준별 구현·테스트 → 검증 → 기능 동결 후 DECISIONS·HANDOFF 정리
