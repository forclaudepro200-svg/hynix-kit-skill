# hynix-verify

AI 채점관이 하는 "문서 주장 vs 증거" 대조를 제출 전에 직접 해 본다. **고치지 말고 먼저 보고한다.**

## 절차

1. **테스트 실행**: 프로젝트의 테스트 명령(package.json scripts, pytest 등)을 찾아 실행하고 통과/실패 수와 실패 이름을 기록한다. 테스트가 없으면 "테스트 없음"으로 기록한다.
2. **성공 기준 추적**: PLAN.md의 기준(C1, C2…)마다 아래를 확인해 표로 만든다.
   - 그 기준을 검증하는 테스트가 있는가(이름에 기준 번호)
   - 테스트가 실제로 통과하는가
   - 판정: 충족 / 부분 / 미충족 / 테스트 없음
3. **거짓 성공 점검**:
   - 처리 행 수가 0이거나 입력보다 크게 줄었는데 성공으로 끝나는 경로가 있는가
   - 예외를 삼키고(`catch`/`except: pass`) 성공을 반환하는 곳이 있는가
   - 테스트가 아무것도 단언하지 않거나 항상 통과하는가
4. **문서 대조**: HANDOFF.md·DECISIONS.md의 각 주장("~를 검증함", "~를 처리함")에 대해 근거가 되는 코드 위치·테스트·커밋이 있는지 확인한다. 근거가 없으면 "근거 없음"으로 표시한다.
5. **실행 확인**: HANDOFF.md의 실행 명령을 실제로 실행한다. 서버라면 `0.0.0.0` 바인딩인지 확인하고 `curl`로 한 번 요청한다. 확인 후 서버를 종료한다.
6. **제출 점검**:
   - `git status`: 커밋 안 된 변경이 있는가
   - README가 요구한 필수 파일·산출물이 모두 있는가. PLAN.md `## 0. 제출물 체크리스트`가 있으면 항목마다 경로 존재·형식·필수 필드를 확인하고 상태 칸을 갱신한다
   - PLAN·DECISIONS·HANDOFF에 빈 칸이나 템플릿 문구가 남았는가
   - 비밀 정보(키, 토큰)나 큰 임시 파일이 들어가 있는가
7. 결과를 VERIFY.md에 쓴다.
   ```
   ## 요약 (한 줄: 제출 가능 / 수정 필요 n건)
   ## 테스트 결과 (명령, 통과/실패 수)
   ## 성공 기준 추적표
   ## 문제 목록 (심각도 높은 순: 위치, 내용, 제안)
   ## 제출 체크리스트
   ```
8. 문제 목록 상위 3개를 화면에 보여 주고 멈춘다. 고칠지는 사용자가 정한다.

## 하지 말 것
- 문제를 발견해도 묻기 전에 코드를 고치지 않는다.
- 실행하지 않은 확인을 "통과"로 쓰지 않는다. 못 한 것은 "미검증"이라고 쓴다.
- 테스트를 통과시키려고 테스트를 수정하지 않는다.
