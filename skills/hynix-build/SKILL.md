# hynix-build

성공 기준 **하나**만 처리하고 멈춘다. 커밋 1개, 테스트 1개 이상, 결정 기록 1줄이 기준마다 남게 한다.

## 토큰 절약 (모든 단계)
- 문서는 **필요한 절만** 읽는다: PLAN은 3절(성공 기준)·4절(데이터 규칙), HANDOFF는 충족표, DECISIONS는 마지막 몇 줄(`grep -n`, `sed -n`, `tail`). 문서 전체를 출력하지 않는다.
- 이미 이 세션에서 읽은 파일은 바뀌지 않았으면 다시 읽지 않는다.
- 언어·런타임·테스트 명령은 AGENTS.md `## 환경`을 따른다. 다른 런타임을 찾는 명령을 실행하지 않는다. 비어 있을 때만 `node --version`으로 한 번 확인한다.
- 데이터는 `head`, `wc -l`, 짧은 집계 스크립트로만 본다. 프로파일은 INTERVIEW.md에 있으면 그것을 쓴다.
- 보고는 아래 형식만, 짧게 쓴다.

## 공통 준비
1. PLAN.md를 읽는다. 없거나 성공 기준 표가 비어 있으면 **구현하지 말고** "PLAN.md 성공 기준부터 정해야 합니다"라고 보고하고 멈춘다. **단, C0(최소 골격)은 예외**: README의 입력·산출물 정보만으로 진행한다.
2. 요청한 기준 ID의 행(기준, 측정 방법, 출처)과 관련 데이터 규칙(PLAN 4절)을 찾는다. "다음 기준"이면 HANDOFF.md 충족표·git log를 보고 아직 안 한 가장 앞 번호를 고른다.
3. 기준이 **모호하면 멈춘다**: 수치·경계(같을 때 포함인지)·예외 처리가 기준이나 출처에 없으면, 업무 담당자에게 물을 질문을 숫자가 들어간 문장으로 1~3개 제시하고 멈춘다. 추측으로 정하지 않는다.

## C0: 최소 골격
- 입력을 읽어 → 최소 처리 → 결과를 내는 한 줄짜리 실행 경로를 만든다. 판정 로직은 비워 두거나 가장 단순하게 둔다.
- 입력 행 수 / 제외 행 수 / 처리 행 수를 출력한다.
- 서버라면 `0.0.0.0`과 `PORT` 환경변수로 띄우고 `curl`로 한 번 확인한 뒤 종료한다.
- 테스트 실행 명령이 동작하도록 테스트 1개(`test_C0_smoke`)를 만든다.
- HANDOFF.md `## 실행 방법`에 실행 명령 한 줄을 적는다.
- 커밋: `C0: 최소 실행 골격`

커밋이 권한 문제 등으로 실패하면 실패 메시지를 그대로 보고하고, 사용자가 직접 실행할 커밋 명령을 한 줄로 제시한다(모든 단계 공통).

## Cn: 기준 하나 구현
1. **계획 제안**: 무엇을 어느 파일에 할지 3줄 이내로 제안하고 승인을 기다린다. 사용자가 "바로 진행"이라고 했으면 생략한다.
2. **테스트 먼저**: `test_Cn_<내용>` 이름으로 테스트를 쓴다. 정상 사례 1개 + 경계값·빈 입력·중복·잘못된 형식 중 이 기준에 해당하는 것을 포함한다. 기대값은 PLAN의 기준과 출처(담당자 발언)에서 가져온다.
3. 테스트를 실행해 **실패하는 것을 확인**한다(이미 통과하면 테스트가 기준을 제대로 검사하는지 다시 본다).
4. **최소 구현**: 이 기준을 통과하는 데 필요한 만큼만 고친다. 판정·계산은 결정론적 코드로 한다. 다른 기준의 기능을 미리 만들지 않는다.
5. **전체 테스트 실행**: 새 테스트 통과 + 기존 테스트가 깨지지 않았는지 확인한다. 깨졌으면 원인을 보고하고, 테스트를 고쳐서 통과시키지 않는다.
6. **커밋**: `Cn: 무엇을/왜` (예: `C2: 임계값과 같으면 합격 처리 (담당자 확인)`)
7. **기록**: DECISIONS.md에 추가한다.
   - 결정 표에 한 줄: 결정, 버린 대안, 근거(PLAN 출처), 검증(테스트 이름과 결과)
   - `핵심 코드 이해 메모`에 한 줄: `파일:함수 — 무엇을 하고, 어떤 입력에서 깨질 수 있는가`
   - HANDOFF.md 충족표의 Cn 행을 `충족 | test_Cn_... 통과`로 갱신한다.
   - 이번 기준에서 사용자가 제안을 수정·거절했거나, 테스트 실패로 처음 구현을 고쳤다면 `AI 제안 검토 기록`에 한 줄 추가한다.
   - 문서 변경도 커밋한다: `Cn: 결정·충족표 기록` (6번 커밋에 합쳐도 된다)
8. **보고하고 멈춘다**:
   - 변경 파일
   - 실행한 테스트 명령과 결과(통과/실패 수)
   - 입력/제외/처리 행 수(해당하면)
   - 미검증 항목과 리스크
   - 다음 기준 제안 1개

## 요구사항이 바뀌었을 때 ("C2 경계값 합격으로 바뀌었어")
1. PLAN.md의 Cn 기준과 출처를 새 발언으로 고친다.
2. DECISIONS.md에 `변경: 이전 → 이후, 근거(누가·언제)` 한 줄을 추가하고, `AI 제안 검토 기록`에도 "이전 구현 → 수정, 이유"를 남긴다.
3. 테스트 기대값을 먼저 고치고 실패를 확인한 뒤 코드를 고친다.
4. 전체 테스트 통과 후 커밋: `Cn: <변경 내용> (담당자 정정 반영)`

## 하지 말 것
- 한 번에 여러 기준을 구현하지 않는다.
- 테스트를 통과시키려고 기대값을 근거 없이 바꾸지 않는다.
- 실행하지 않은 테스트를 통과로 보고하지 않는다.
- 패키지를 묻지 않고 설치하지 않는다. `git push`를 하지 않는다.
